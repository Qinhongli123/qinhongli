Skill（AI 技能包）

一句话理解：一份写给 AI 看的"岗位说明书 + 操作手册"——用结构化文件告诉 AI：你有哪些新本事、什么时候该用、具体怎么一步步做。

🏠 概念关系图 · Agent · 大模型的上下文 · Skill

1概念定义

大白话版：你新招了一个聪明但啥都不懂的实习生（大模型/Agent），与其每次干活前口头交代一遍流程，不如写一份《新员工操作手册》放进他的工位。Skill 就是这份手册：把某项能力的触发条件、使用流程、注意事项写成一个标准文件（如 SKILL.md），AI 每次要干活时先读手册再动手。
规范定义：Skill 是一种声明式描述的 AI 能力扩展单元：以结构化文件（典型如 SKILL.md，含 YAML 元信息 + Markdown 正文）定义能力的名称、适用场景、输入输出约定与执行步骤，由 AI 平台在匹配到适用场景时按需加载，从而在不修改模型本体的情况下赋予模型新的、可复用的、行为稳定的专业能力。

2核心机制

📄 声明式描述

用一份文件说清"我是什么、何时用、怎么用"。元信息（名称、描述、版本）供平台检索匹配；正文（流程、规范、示例）供模型执行时阅读。

⚡ 按需加载

平时不占用上下文窗口；只有当用户请求命中技能的适用场景时，才把 SKILL.md 注入上下文。既扩展了能力，又不浪费宝贵的窗口空间。

🔌 输入输出约定

明确规定调用时需要哪些输入（如概念名、专业背景）、产出什么（如六模块 HTML 学习资料）。约定越清晰，AI 的输出越稳定。

📦 可分享、可版本化

Skill 本质是文件夹+文件，天然适合用 Git 管理、分享复用。别人 clone 下来放进自己的 skills 目录就能用。

3应用案例（广告学视角）

案例：本作业本身就是一次 Skill 实践
我把"生成概念学习资料"这件事做成了 concept-learning Skill：固定六模块产出结构（定义→机制→案例→辨析→自测→来源）、固定自检清单。以后再遇到任何新概念（比如"计算广告""归因模型"），不需要重新设计资料框架，直接调用这个 Skill，产出的资料结构始终统一、质量可控。
案例：团队的"提案 PPT 风格" Skill
广告公司可以把提案 PPT 的制作规范（公司模板、字体、页数结构、必含的分析框架）写成一个 Skill，分享给全组。从此让 AI 生成提案初稿时，人人产出的 PPT 骨架都符合公司标准——把"老带新口口相传的经验"沉淀成了"可复制的组织资产"。

4概念辨析：Skill ≠ 工具 ≠ 提示词模板

对比维度工具（Tool）提示词模板（Prompt）Skill（技能包）
本质一段可被调用的程序/接口一段写好的指令文本结构化的能力描述文件（说明+流程+资源）
谁来执行外部程序执行，AI 只发起调用AI 按文本模仿AI 读完后指挥自己+组合工具执行
加载方式预先接入、常驻可用每次手动粘贴进对话平台按场景自动匹配、按需加载
可组合性单一功能点孤立片段可包含流程、示例、附属资料，还能调用工具
广告类比设计软件里的某个功能便利贴上的提醒标准作业流程 SOP 手册
三者关系一句话：Skill 是"会用工具的成套方法"——一份 Skill 可以指挥 AI 在合适时机调用多个工具，远比单个工具或一段提示词更接近"专业能力"。

5自测问题（点击展开参考答案）

Q1：为什么 Skill 采用"按需加载"而不是"常驻上下文"？
上下文窗口是稀缺资源（详见第二篇）。技能库可能有几十上百个 Skill，全部常驻会挤占窗口、降低性能还增加成本。按需加载让平台平时只保留技能的"名称+描述"用于匹配，命中场景后才加载完整说明，实现能力扩展与窗口占用的平衡。
Q2：SKILL.md 里的 YAML 头部（name/description）和 Markdown 正文，分别写给"谁"看？
YAML 头部主要写给平台/系统看：用于检索、匹配用户请求该不该触发这个 Skill；Markdown 正文写给模型看：触发后模型要照着它执行具体流程。一个管"要不要用"，一个管"怎么用"。
Q3：把同一个"写小红书文案"的需求分别做成提示词模板和 Skill，最大的区别是什么？
提示词模板需要你记得主动粘贴，且只能覆盖单一场景；Skill 由平台自动识别场景触发，还可以包含多步流程、自检清单、附属资料（字体、示例、禁用词表），产出更稳定。模板是"给模型的便签"，Skill 是"给模型的制度"。
Q4：Skill 与 Agent 是什么关系？
Agent 是"会自主干活的执行者"，Skill 是"执行者掌握的成套方法"。Agent 的能力天花板之一就是它掌握多少高质量 Skill：同一个 Agent，装上"提案 PPT Skill"就能做提案，装上"舆情监测 Skill"就能做监测。Skill 是 Agent 能力的模块化扩展（详见概念关系图）。
